# Navi MVP 스펙 — 요구사항 정제·확인 루프

> 목표: **개발자에게 오기 전에 담당자가 확인을 최대한 끝낸 상태의 태스크를 만든다.**
> 원칙: 전면 개편 없이 기존 화면(업무 보드, 태스크 상세, 분석)의 이음새를 수리한다. 기능은 최소로, 검증은 빨리.

---

## 범위 1. 태스크 생성 — 유형 템플릿 + 예제 텍스트

- 태스크 생성 시 유형 선택: **신규 기능 / 기존 기능 수정 / 자동화·배치 / 정책 변경**
- 유형 클릭 시 본문에 예제 텍스트가 채워진 템플릿 삽입 (placeholder가 아니라 실제 텍스트)
- 예제 값은 `(예: ...)` 마커로 표기해 실제 값과 혼동 방지
  ```
  정책:
  - (예: 생일인 유저에게 적립금 5,000원 발급)

  배치 주기:
  - (예: 매일 09:00 — 실제 주기로 수정하세요)

  세부사항:
  - (예: 발송 채널 — 알림톡, 실패 시 LMS 대체 발송)
  - (예: 실행 결과 리포트 — 슬랙 #navi-batch 채널에 발송 건수 게시)

  예외 조건:
  - (예: 마케팅 수신 동의를 하지 않은 유저에게는 알림톡을 보내지 않는다)
  - (예: 이미 발급받은 유저에게 중복 발급하지 않는다)
  ```
- 섹션 구성은 유형별 고정. **세부사항·예외 조건 섹션 필수** (분석·검수의 기준). "목적/배경" 등 안 채워지는 섹션은 넣지 않는다
- 세 축의 역할 분담: **정책**(무엇을 한다) → **세부사항**(어떤 값으로 — 시점·기간·채널·문구·노출 위치) → **예외 조건**(언제 제외한다). 세부사항이 catch-all이 되지 않도록 예제는 `항목 — 값` 형태로 제시한다
- 고정 문구(알림톡·푸시 등)가 필요한 유형은 세부사항 아래 `### 알림톡 템플릿` 코드블록을 둔다. 블록 안 예제도 `(예:` 마커를 유지해 마커 검사에 걸리게 한다
- 완료 조건·인수 기준은 담당자에게 요구하지 않는다 — 개발·QA의 언어라 정상 흐름을 한 줄 반복하는 답변만 나온다. 담당자가 실제로 쥐고 있는 정보는 **제외 대상·엣지케이스**이고, 개발자 역질문의 대부분도 여기서 나온다
- 예외 조건 예제는 유형마다 2~3줄로 제시한다. 한 줄이면 한 줄만 적고 끝내므로, 항목 수 자체가 요구사항 품질인 이 섹션에서는 복수 제시가 필요하다
- 템플릿은 하드코딩하지 않고 레포에 md 파일 4개로 관리
- "분석 시작" 클릭 시 `(예:` 마커 잔존 검사 → "예제 텍스트 N건이 남아 있습니다" 경고 (문자열 검색)

## 범위 2. 정제 — 에이전트가 문서 수정을 "제안"

핵심 설계: **에이전트는 문서를 직접 쓰지 않는다. 변경 제안(proposal)을 만들고, 쓰기 권한은 사용자의 수락 버튼에만 있다.**

플로우:

```
사용자 메시지
  → LLM 호출 (시스템 프롬프트 + 문서 현재 상태, stateless)
  → 구조화된 제안 반환
  → 서버 검증 (섹션/필드 enum, 타입) — 실패 시 폐기, 자동 재시도 1회
  → proposal 레코드 저장 (pending)
  → 문서 위에 diff 렌더링 (서버가 diff 계산, LLM이 아님) + 수락/거부 버튼
  → 수락: 대상 섹션의 현재 값 == 제안 시점 값 확인(섹션 단위 낙관적 잠금)
          → 적용, 문서 버전 +1, 활동 로그 "Navi 수정(사유) → 사용자 승인"
  → 거부: 사유 입력 → 사유를 담아 재요청 → 새 proposal
```

- 변경 단위: **섹션 전체 교체** (문자 단위 패치보다 견고, 템플릿 섹션 고정 덕에 enum 가능)
- 도구: `replace_section(section, new_content, reason)` / `update_field(field, value, reason)` / `no_change(message)`
- 실서비스: tools + `tool_choice: {type: "any"}` (도구 강제 + no_change 탈출구 + 서버 검증 + 재시도 1회)
    - 데모는 환경 제약으로 JSON 계약 출력 방식으로 검증 완료 — 파이프라인은 운송 수단과 무관하게 동일
- 본문 정본(canonical)은 마크다운. 블록 에디터와의 정밀 통합은 보류
- proposal 테이블: `id, task_id, tool, input(JSON), base, status(pending/accepted/rejected/stale), created_at`
- 엔드포인트 3개: `POST /tasks/:id/chat`, `POST /proposals/:id/accept`, `POST /proposals/:id/reject`

## 범위 3. "개발 준비됨" 게이트

Definition of Ready의 자동 판정. 새 기능이 아니라 기존 조각의 조합.

체크 3개 (모두 자동 또는 반자동):

1. 예제 마커 `(예:` 0건
2. 분석 1회 이상 실행됨
3. 분석이 뽑은 미결정 사항 전부에 답변 체크됨 (체크는 수동으로 시작)

- 통과 시 카드에 **"개발 준비됨" 뱃지**
- 미통과 상태로 Todo 이동 시 경고: "미결정 N건이 남아 있습니다" (강제 차단은 아님)
- 개발자 전용 컬럼은 만들지 않는다

## 보류 (검증 후 판단)

- 인터뷰형 태스크 생성 (템플릿의 업그레이드 경로 — 템플릿만으로 충분하면 안 만든다)
- 유사 과거 태스크 프리필, 코드베이스 기반 확인 질문
- 분석 탭 통합·버전 간 diff, 결정 카드(DRI/기한/침묵 승인), Slack 리마인드
- 확정 스펙 핸드오프 (md export / MCP)
- 산정치 dev-in-the-loop (공수 예측을 개발자 확인 후 관계자에게 공유 — 현재는 분석 결과 하단 면책 문구로 대체)
- 칸반·전반 UI 개편 (하지 않는다 — "자체 보드 유지 vs Asana에 붙는 레이어" 결정은 별도 논의)

## 검증 지표

| 대상  | 질문                                | 신호                         |
|-----|-----------------------------------|----------------------------|
| 템플릿 | 비개발자가 개발자에게 묻지 않고 분석 가능한 초안을 만드는가 | 초안 작성 중 질문 횟수              |
| 템플릿 | 예제 값이 미수정으로 남는가                   | 마커 경고 발생 빈도                |
| 정제  | diff 수락/거부를 스스로 판단하는가             | "이거 눌러도 돼요?" 질문 여부, 재제안 횟수 |
| 전체  | 게이트 통과 태스크에 개발자 역질문이 줄었는가         | 태스크당 역질문 수 (도입 전 대비)       |

## 구현 순서

1. 범위 1 — 템플릿 md 4종 + 삽입 + 마커 검사 (≈1일)
2. 범위 2 — proposal 파이프라인 (데모 코드의 [1]~[5]를 백엔드로 이식)
3. 범위 3 — 게이트 (조건문 조합)
